## Why X Wallet

X Wallet is built for people who want a real self-custodial wallet on their
phone and on their desktop, without an account or a cloud.

- **Self-custodial by design.** The recovery phrase and signing keys stay on
  your device. There is no account, no custody, and no sign-up.
- **Android and Linux.** A signed Android APK with a native KDF and a real
  `.deb` with a desktop launcher, upgrade path, and user-data preservation.
- **Cold signing built in.** Create an offline signer and an online companion
  from the same open-source application; private-key-only wallets can pair and
  sign too.
- **Multiple wallets in one vault.** Add, switch, rename, and remove wallets
  with one vault password.
- **Any vault password, honestly scored.** Short and long passphrases are
  accepted; a live strength meter shows Very weak through Very strong.
- **USDT and USDC by default.** BNB, USDT, and USDC appear in every BSC wallet
  with contracts read from the chain.
- **Verified public RPC doors.** Default nodes include BNB Chain, PublicNode,
  1RPC, Blast, and 48.club public endpoints.
- **Privacy is a setting, not an afterthought.** Tor, SOCKS5, HTTPS proxies,
  custom RPC nodes, TLS pinning, and fail-closed routing.
- **Review before you sign.** Full recipient, chain, nonce, fee, maximum-cost,
  and calldata checks, with hold-to-confirm.
- **Encrypted local history.** Vault, activity log, and receipts are protected
  at rest with Argon2id and XChaCha20-Poly1305.
- **Free and open source.** AGPL-3.0-or-later, no subscription, no paywall, no
  ads, and no analytics SDK in the locked dependency inventory.
- **Evidence, not slogans.** 67 test files, 382 test declarations, mutation
  testing, CodeQL, SBOM, a reproducible build, and an independent ethers.js
  cross-check.
- **Android hardening.** Native Argon2id, background/idle vault lock, 6-digit
  PIN rules, optional wipe-after-failures, FLAG_SECURE, obscured-touch
  rejection, R8/obfuscation, and a verified signer gate.

## Download, verify, install

Get the latest release from:

**<https://github.com/jackh0006/X-Wallet/releases/latest>**

```bash
# 1. Download the package and checksums from the release page.
# 2. Verify the download.
sha256sum x-wallet-1.5.1-amd64.deb
sha256sum -c SHA256SUMS
gpg --import x-wallet-signing-key.asc
gpg --fingerprint CC819EF5E109A1518E840379D8C0CEC84BCCE06B
gpg --verify SHA256SUMS.asc SHA256SUMS

# 3. Install.
sudo apt install ./x-wallet-1.5.1-amd64.deb
```

The Debian package is `x-wallet`. It replaces `bnb-wallet`, preserves the
existing user-data directory, and keeps `/usr/bin/bnb-wallet` as a
compatibility alias.

The release is signed with owner key
`CC819EF5E109A1518E840379D8C0CEC84BCCE06B`. Verify the fingerprint through an
independent channel before trusting it.

### Android

Download the APK that matches the phone:

- `x-wallet-1.5.3-android-arm64.apk` — almost every modern Android phone,
  including the Huawei Y9 2019.
- `x-wallet-1.5.3-android-universal.apk` — ARM 32-bit and 64-bit phones if you
  are not sure about the CPU. It no longer carries the x86_64 emulator slice,
  so it is smaller than the 1.5.1 universal build.

**1.5.3 uses a new Android signing identity**
(`2a96a384eb0db55bb4fb0fb2107df386ecc595b38bc46225ef9b18309d93ba9a`).
Android will not install it as an in-place upgrade over a 1.5.1 build signed
by `db12869c…9748d3`. Export a portable backup first, then uninstall the old
app and install 1.5.3. Uninstalling removes app data; the backup is the
recovery path.

The Android app uses the same logo, label, vault, tokens, spending controls,
English-only UI, and cold-signing protocol as Linux. It ships the native
Argon2id library, clears signing keys when it leaves the foreground, rejects
overlay touches, and blocks screenshots. Install it with the Android file
manager. Android asks you to allow installs from the file manager once.

Tor on Android uses **Orbot**; open [the Android guide](docs/ANDROID.md) for the
short setup steps. Android uses the system file picker for backups and cold
payloads, so the app never needs broad storage permission.

## Quick start

1. Install X Wallet and open it from your application menu.
2. Create a new wallet or import an existing BIP-39 recovery phrase.
3. Write the recovery phrase on paper and verify the backup.
4. Check the derived address against an independent record.
5. Receive a small test amount first, then send a small test transaction.
6. Choose a custom RPC node or enable Tor/SOCKS routing if you want more
   control over network privacy.

## Feature tour

### Encrypted local vault

The vault uses Argon2id (64 MiB, t=3, p=4) and XChaCha20-Poly1305 with a
two AEAD wrappers around a random data key: the password wrapper opens the payload, and the device wrapper adds at-rest defense in depth. The device wrapper is not a required second factor.
Writes are atomic, permissions are hardened, and the v1 vault format migrates
on save.

### Transaction review that shows the details

Before signing, X Wallet shows the full checksummed recipient, chain, nonce,
fee fields, maximum cost, and token calldata. Hold-to-confirm prevents a
single accidental tap. Address-poisoning checks and an uncertain-broadcast
state are part of the flow.

### Cold and offline signing

Cold mode blocks every app-initiated network call (RPC, prices, explorer history and node probes). The binary still links networking code; OS-level isolation is documented in the cold-wallet guide. The online companion prepares the
request and broadcasts the signed result. Pairing, expiry, replay protection,
and field allowlists are enforced, and a separate ethers.js implementation
reconstructs and verifies the signed bytes.

### Privacy routing

Choose direct HTTPS, HTTP/HTTPS proxy, SOCKS5, or Tor. Standard certificate and
hostname validation always runs before any SPKI pin. Privacy mode fails closed;
it does not silently fall back to a direct connection.

### Local history and receipts

Activity records and receipt images are stored in encrypted local envelopes.
Lock, PIN backoff, idle lock, and erase-all-data controls are built in.

## Risk and responsible use

X Wallet is a self-custodial software wallet. You control the keys, so you also
control the security boundary.

- **Device security.** A compromised operating system, malware, or an attacker
  with the same user account can read an unlocked session.
- **Recovery phrase.** Write it on paper and store it offline. There is no
  recovery service.
- **RPC trust.** A node operator can see your addresses and requests. Use your
  own node or the privacy routing options for more control.
- **Large amounts.** For significant holdings, split the balance across
  vault accounts and use cold/offline signing with the operating controls in
  `docs/RISK_CONTROLS.md`.
- **Network fees.** Blockchain fees are paid to the network, not to X Wallet.
- **Download integrity.** Download only from the official release page, verify
  the published SHA-256, and verify `SHA256SUMS.asc` against the signing
  fingerprint obtained independently.

# Security policy

X Wallet is AI-assisted and self-assessed personal-use software wallet. Do
not report a security issue in a public GitHub issue and do not include seed
phrases, private keys, vault files, passwords, or live transaction data in a
report. AI assistance and self-assessment are not independent review.

## Reporting a vulnerability

Email jackh109867@gmail.com with:

- a concise description and affected version/commit;
- safe reproduction steps using only throwaway keys and a local/test network;
- impact and any suggested mitigation.

The maintainer will acknowledge reports privately, assess impact, prepare a
fix, and coordinate disclosure with the reporter. Target first response:
within 7 days; fix or mitigation plan for a confirmed high issue: within 30
days. There is no bounty program, and this project does not claim a funded
bounty or a long public track record.

### PGP

Release and report key fingerprint:

```
CC819EF5E109A1518E840379D8C0CEC84BCCE06B
```

Public key: `docs/keys/x-wallet-signing-key.asc`. Verify the fingerprint
through an independent channel before trusting it. Encrypt sensitive report
details to this key if you can.

### Safe harbour

Good-faith research on your own test keys, a local node, and testnet is
welcome. Do not test against other people's wallets, mainnet funds, or
third-party infrastructure without permission.

## `SECURITY_LIMITATIONS.md`

# Security Limitations

This file is the correct place for material scope and risk. Advertising pages
should link here instead of hiding these facts.

- **No independent audit.** The project publishes an internal self-audit, not a
  third-party audit or certification.
- **Android runtime not tested here.** The APK build, ABI, permissions, and
  signatures are verified, but no physical phone was connected during this
  audit. Use the Huawei Y9 2019 checklist.
- **Cold wallet is a demonstration/prototype.** Physical air-gap, two-device,
  and hardware-isolation security are NOT TESTED.
- **Large-value custody is not certified.** Small disposable mainnet testing is
  the current honest limit; large amounts require independent review and
  device-level controls.
- **Compromised OS.** Malware, a rooted phone, or a same-UID attacker can read
  an unlocked session.
- **Managed memory.** Dart/Android cannot guarantee secure erasure; `mlockall`
  is Linux-only and best-effort.
- **RPC trust.** Balances, nonces, fees, and history come from the chosen node;
  a lying provider can mislead the review screen but cannot forge a local
  signature.
- **Fixed-path reproducibility.** Different absolute build paths may differ
  because Flutter embeds paths.
- **No physical hardware-wallet support** is claimed in 1.x.

# Threat Model — X Wallet

Created by jackh0006 (jackh109867@gmail.com)

This page states plainly what the wallet protects against, what it does not,

|---|---|---|

## What this wallet defends against

1. **Stolen vault file.** A copy of `bnb-wallet-vault.bnb` needs the
   password. The device secret adds defense in depth on the same machine,
   but it is not a required second factor. Moving the file
   to another machine, or exfiltrating it via malware, yields nothing.
2. **Weak passwords / offline brute force.** Any password guess costs an
   Argon2id run (64 MiB, t=3, p=4) per attempt, per salt. There are no
   shortcuts in the file: parameters live in an authenticated header.
3. **Tampering / KDF abuse.** The entire header (magic, version, KDF
   parameters, salt) is authenticated data for every AEAD box. The parser
   also accepts only the published fixed Argon2id profile before it derives a
   key, so a hostile backup cannot request unbounded KDF memory or CPU.
4. **Malicious contacts / address poisoning.** The send dialog shows the
   full grouped, checksummed address and warns when a recipient shares a
   4+ character prefix or suffix with an address already on the device —
   the classic "drip address" scam.
5. **Contract-recipient mistakes.** Before confirmation, the app reads the
   recipient's on-chain code and warns when it is a contract.
6. **Shoulder surfing & screen capture.** Linux desktops have no reliable
   application-level equivalent to protected screenshots; this is a
   documented gap, see below.
7. **Idle exposure.** Auto-lock (configurable; 60 s default) and an
   immediate lock on backgrounding clear keys from memory.
8. **PIN guessing across restarts.** The backoff window is persisted in
   secure storage, so killing the app does not reset the counter.
9. **Keyboard side channels for seeds.** Seeds are entered by tapping
   official BIP-39 words through a picker; the IME/keyboard never receives
   the phrase, so gesture-typing traces and auto-learn dictionaries stay
   clean.
10. **Network observers (when Tor mode is on).** All RPC and explorer
   traffic is routed through a local SOCKS5 connector (Tor). DNS travels
   inside the tunnel. If the proxy is down, calls fail — the app never
   silently falls back to a direct connection.
11. **Cold-wallet field substitution.** A signed response is accepted only
   if its raw EIP-1559 transaction matches the exact pending request field
   by field (chain, nonce, fees, gas limit, recipient, value, calldata),
   its hash matches the raw bytes, and its signature recovers to the paired
   address. A changed request cannot reuse an old signature.
12. **Cold-wallet replay.** A request id can be signed once; a response is
   accepted only while its request is pending; a transaction hash already
   broadcast is refused. The node's returned hash must equal the locally
   computed hash, otherwise the wallet reports an unknown outcome and does
   not resend automatically.
13. **TLS interception with a trusted-but-wrong certificate.** Optional
   SPKI pinning runs *after* standard CA and hostname validation. A pin can
   never make an untrusted or wrong-host certificate acceptable. Pinned
   HTTP CONNECT is refused rather than silently downgraded.

## Cold-wallet threats (implemented flow)

The cold flow separates the seed holder (offline) from the network holder
(public pairing only). Its security depends on the user comparing the pairing
fingerprint and reviewing the transaction on the cold screen.

| Threat | Control | Residual risk |
|---|---|---|
| Malicious pairing replaces the recipient addresses | Pairing is public data; the fingerprint is derived from the first address and must be compared on both devices out-of-band | If the user skips the fingerprint comparison, a substituted pairing is accepted |
| Online companion prepares a dishonest request (wrong recipient/fee) | Cold device decodes and displays the exact request; the user must approve it | A user who does not review the cold screen can sign a dishonest request |
| Signed response substitutes fields | Full field-by-field comparison, request hash, raw parse, `r`/`s`/`yParity`, transaction hash, signer recovery | A bug in the shared codec could affect both sides; the independent ethers.js check is the cross-check |
| Replay of a signed response | Single-use request id, pending-request requirement, broadcast-hash burn list | Reinstalling the app clears local replay state; the chain nonce still prevents a second valid transaction with the same nonce |
| Unsigned request sits on disk too long | 30-minute default lifetime, 24-hour hard cap, expiry checked at sign and verify time | Clock skew beyond 5 minutes causes refusal, not acceptance |
| QR/file channel is observed | Envelopes contain only public tx data and public addresses | The channel is not confidential; it does not need to be |
| Cold device has no network but is compromised | Cold mode performs no app-initiated network calls; the binary still links network code; keys stay in process memory while unlocked | A compromised OS can read memory or the seed; out of scope |
| Online companion is compromised | It never holds a key, and it cannot forge a signature for the paired address | It can refuse service, lie about fees, or withhold a response |

The cold protocol is not a substitute for a hardware wallet: the seed exists
in the cold device's process memory while unlocked, and there is no secure
element or trusted display.

## What this wallet does NOT defend against

Honesty section. These are real limits, not corner cases.

- **A compromised device or OS.** Keyloggers, rootkits, screen readers, or
  a malicious keyboard on a rooted/android-modified device can defeat any
  local protection, including the secure store. Out of scope.
- **Malicious RPC endpoints or explorer API.** A lying endpoint can show
  fake balances or reflect the wrong history. The wallet does not verify
  chain data independently (light-client proofs are not implemented).
- **On-chain privacy.** Blockchains are public ledgers. Any address you
  transact with, and everyone running a node, can link amounts and
  counterparties. Tor hides *where you asked*, not *what the chain says*.
- **ISP/traffic analysis with Tor on.** Your ISP still sees that you are
  sending traffic to Tor (or to a bridge endpoint). It does not see the
  destinations inside the tunnel unless it also runs the guard.
- **Tor entry/exit observers.** A malicious guard with a malicious exit
  could correlate traffic patterns for non-TLS traffic; the wallet is
  HTTPS-only, so exits see ciphertext only.
- **Clipboard.** Addresses and amounts can be copied. Malware reading the
  clipboard can substitute addresses. Always compare the full grouped
  address in the confirmation dialog.
- **Linux FLAG_SECURE gap.** On desktop, screenshots are not blocked at
  the toolkit level. Lock your session when leaving the machine.
- **Flash shred guarantees.** "Erase all data" overwrites the vault with
  random bytes before deletion, but wear-leveling means copies can linger
  in flash. Deleting the device secret removes the app's device factor, but a
  retained vault copy plus the password remains decryptable. Crypto-erasure
  is not a guarantee here.
- **Seed loss.** There is no recovery. If you lose the seed phrase and
  forget the vault password, the funds are gone. The app cannot fix this.
- **User error.** Sending to the wrong (valid) address, losing the seed,
  or confirming a scam transaction is out of scope for any software.
- **Cold-flow user checks.** The cold device must display and the user must
  review the recipient, amount, fee cap and calldata. The software binds the
  bytes but cannot force a human to read the screen. The pairing fingerprint
  must be compared on both devices; skipping that check defeats the pairing
  control.
- **Cold-mode field testing.** The flow is covered by automated tests and a
  fake broadcast, not by a documented two-physical-device exercise.
- **Camera QR on Linux.** Not implemented; file and paste are the transports.
- **Historical credential exposure.** The old Android release keystore was
  committed publicly and remains compromised. It is not a Linux package
  credential and Android work is outside this assessment.
- **Memory locking is best-effort.** `prctl(PR_SET_DUMPABLE, 0)` and the core
  limit are asserted on Linux; `mlockall` can fail under a low memlock limit.
  Windows/macOS are not covered by the kernel-state test.
- **Independent verification — honest status.** The cryptography sits on
  published, reviewed primitives (Argon2id, XChaCha20-Poly1305, HKDF — from
  the pinned `cryptography` package; secp256k1 via `web3dart`; SOCKS5 from
  `socks5_proxy`). The EIP-1559 serialization is project code, because the
  available RLP helper encoded byte strings incorrectly; it is cross-checked
  against ethers.js 6.17.0 in `verification/verify.cjs`. What no software
  author alone can hand you is a **third-party security audit of this
  release** — if you plan to hold serious value here, require one before

## When Tor mode is useful, and when it is not

Useful: reducing which nodes see *your IP asking about your addresses* —
useful if your address is linked to a publicly known identity and you do
not want the RPC provider to correlate it.

Not useful: hiding activity from the chain, hiding identity already baked
into past transactions, or bypassing a malware/keyboard compromise.

Crypto primitives are provided by the `cryptography` package (XChaCha20-

One serialization component is project code: the canonical EIP-1559/RLP
codec in `lib/cold_tx_codec.dart`. The available `rlp` helper encoded every
`List<int>` as an RLP list, so addresses and calldata were serialized

## Vault envelope v2 ("BNBVL004", version byte 2)

Stored at `<app-support>/bnb-wallet-vault.bnb`, base64 of the binary
envelope. Total binary layout, in order:

```
offset  size  field
0       8     magic   "BNBVL004" (0x42 0x4e 0x42 0x56 0x4c 0x30 0x30 0x34)
8       1     version 0x02
9       4     Argon2id memory KiB, uint32 LE   (65536)
13      4     Argon2id iterations, uint32 LE   (3)
17      4     Argon2id parallelism, uint32 LE  (4)
21      16    salt (random)
37      24    paperBox nonce
61      32    paperBox ciphertext  (DEK, 32 bytes)
93      16    paperBox MAC (Poly1305)
109     24    deviceBox nonce
133     32    deviceBox ciphertext  (same DEK)
165     16    deviceBox MAC
181     24    payloadBox nonce
205     N     payloadBox ciphertext (JSON vault)
205+N   16    payloadBox MAC
```

AAD for ALL THREE AEAD boxes is bytes [0..37) — the header including
parameters and salt. Consequences:

- Any modification of magic, version, KDF parameters or salt makes every
  box fail authentication. Parameter downgrade attacks are impossible
  without also holding the DEK (i.e. having broken the wrappers already).
- The payload integrity covers the header: cut-and-mix attacks across
  historical vaults fail because each vault has its own random salt.

Keys:

```
KEK_pw   = Argon2id(password, salt, 64 MiB, t=3, p=4, 32-byte tag)
KEK_dev  = HKDF-SHA256(ikm=deviceSecret, salt=0x00×32,
                       info="bnb-wallet/device-kek-v2", L=32)

Where deviceSecret lives: Android/iOS keep it in the platform keyring
(Android Keystore-backed), read at most once per session. Desktops (Linux,
macOS, Windows) deliberately keep it in an owner-only (0600) drawer file
beside the vault in the app's data directory — the Linux keyring plugin
performs libsecret calls synchronously inside the GTK window thread, which
froze weak machines mid-wallet-creation. Machine binding is defense-in-depth, not a required second factor: on Linux
the device secret is an owner-only file beside the vault, so an attacker who
copies the whole data directory and knows the password can open the vault.
The password wrapper alone is sufficient to recover the payload. Existing vaults
migrate once (keyring → drawer on the first vault operation after the
update); if a vault's keyring secret cannot be read, the wallet retries once
and FAILS CLOSED — it never mints a replacement that would orphan the vault.
DEK      = 32 random bytes (CSPRNG), never stored in the clear
paperBox = XChaCha20-Poly1305(KEK_pw,  DEK, AAD=header)
deviceBox= XChaCha20-Poly1305(KEK_dev, DEK, AAD=header)
payload  = XChaCha20-Poly1305(DEK, plaintext-JSON, AAD=header)
```

## Argon2id backend and measured cost

The production parameters are fixed at **64 MiB, t=3, p=4, 32-byte tag**
(RFC 9106 low-memory profile). The implementation is selected in
`lib/kdf.dart`:

1. The reference C Argon2 library bundled by `dargon2_flutter`
   (`libargon2.so` on Linux, `argon2.dll` on Windows, the macOS dylib), or
   the platform's `libargon2.so.1`.
2. The pure-Dart `cryptography` Argon2id only when no native library can be
   loaded. This is the same algorithm and parameters, but much slower.

Android 1.5.0 ships the same reference C library as `libargon2-arm.so`,
built from `android/app/src/main/cpp/` and loaded through the FFI path in
`lib/kdf.dart`. The 64 MiB / t=3 / p=4 parameters are identical to Linux. The
release APK contains that library; device-level timing is **NOT TESTED** in this
environment.

Measured on the release-check machine (Ubuntu 24.04, 2 physical cores,
3.8 GiB RAM, Flutter 3.47.6 / Dart 3.13.5): **344 ms** for one 64 MiB,
t=3, p=4 derivation through the native reference library. The same
derivation through the debug-mode pure-Dart fallback took roughly **110 s**,
which is why the native path is the production requirement and why the
fallback must never be silently accepted for a release.

Tests:

- `test/kdf_production_test.dart` asserts the fixed parameters, cross-checks
  the native output against the independent pure-Dart Argon2id at 1 MiB, and
  performs one real 64 MiB vault round-trip with a 60 s performance guard.
- Envelope/format suites use `VaultCipher.debugKdfOverride`, an
  assert-guarded test seam compiled out of release builds. It changes no
  production parameter and cannot be reached in a release binary.

A time-out, OOM, or native-library crash is recorded as `FAILED` or
`INCOMPLETE`; it is never treated as a passing KDF test.

Decryption opens both wrappers and compares the two recovered DEKs in
constant time; a mismatch ("both boxes authenticate but disagree") is a
tampering indicator and fails closed. The payload is then decrypted with the
password-derived DEK, so the password wrapper is sufficient on its own; the
device wrapper is an additional at-rest factor, not a required one. Any failure surfaces one generic
message — "Wrong password, device key unavailable, or corrupted vault" — so
there is no oracle that says which factor was wrong.

Device secret: 32 fresh CSPRNG bytes, base64 in the platform secure store
under key `device_secret_v2` (Android: Keystore-backed
flutter_secure_storage; Linux: libsecret). It is created on first vault
write and destroyed by "Erase all data". If the secure store is unreadable,
vault operations fail closed with DeviceKeyException rather than weaken.

## Legacy read-only path (v1, "BNBVL003", version byte 1)

v1.0.2 envelopes are single-box: header(AAD) ‖ nonce ‖ ct ‖ mac, keyed by
Argon2id(password, salt) directly. v1.0.3 accepts them with the same
parameter floor and upgrades nothing silently: the next vault save re-wraps
the data in v2. The version byte must be 1 for the v1 path.

## App-lock PIN

- Record format: `a2:<saltB64(16 bytes)>:<hashB64(32 bytes)>` in secure
  storage key `app_lock_pin_hash`.
- `hash = base64(Argon2id(pin, nonce=ascii(saltString), 64 MiB, t=3, p=4))`
  — the base64 salt string itself (22 bytes) is the Argon2 salt, so the
  record is deterministic for a given PIN+salt.
- Comparison is constant-time over the raw bytes.
- Records without the `a2:` prefix (v1.0.2 SHA-256) are refused and
  deleted; the lock screen then takes the user to a fresh setup.
- Failed-unlock backoff: after the n-th failure, the next attempt waits
  `min(2^(n-1), 900)` seconds. State is `"<count>:<untilEpochMs>"` in
  secure-storage key `app_lock_backoff`; reading the remaining window
  re-anchors it to "now + remaining", so booting backward/forward does
  not reset it. Vault password attempts are already rate-limited by
  Argon2id's cost.

## Cold-wallet transaction format (EIP-1559)

Implemented in `lib/cold_tx_codec.dart`; used by the cold signer, the strict
response verifier and the online broadcast gate.

Unsigned payload:

```
0x02 || rlp([
  chainId, nonce, maxPriorityFeePerGas, maxFeePerGas,
  gasLimit, to, value, data, accessList
])
```

Signing digest: `keccak256(unsigned payload)`. Signed payload appends
`yParity, r, s` to the same list. `yParity` is 0 or 1. `r` and `s` must be in
`[1, n-1]` and `s <= n/2` (low-s); the parser rejects non-canonical RLP,
non-minimal integers, trailing bytes, wrong field counts and access lists
(the cold protocol does not support them).

The internal `ColdTxSignature.v` stores the **full ECDSA recovery id** (0–3),
while the serialized EIP-1559 transaction contains only `yParity`. The
verifier checks that `v & 1 == yParity`, parses the raw transaction, compares
every field and the transaction hash, and recovers the signer with secp256k1.
Exactly one recovery candidate must match the paired address. No private key
or seed is stored in a request or response.

The independent fixture is in `verification/fixture.json`; it uses the public
Hardhat/Anvil test mnemonic (`test test ... junk`) and no funded key. The
fixture values are reproduced by ethers.js, not accepted on trust from the
Dart implementation.

## TLS SPKI pinning

`lib/net/privacy_client.dart` performs a normal `SecureSocket.connect` with
standard CA and hostname validation first. If the node has pinned SPKI
hashes, the peer certificate's SubjectPublicKeyInfo is extracted and hashed
with SHA-256; the base64 value must match one of the pins. A wrong pin closes
the connection. A pin cannot make an untrusted chain or wrong hostname
acceptable, and an empty pin list fails closed.

SPKI extraction follows RFC 5280: the subjectPublicKeyInfo is element 6 of
`TBSCertificate` when the explicit `[0]` version field is present, element 5
otherwise. The earlier code used index 7 for v3 certificates, which hashed
the extensions block instead of the public key. `test/tls_pinning_test.dart`
compares the Dart result with OpenSSL's independent extraction.

Pinned HTTP CONNECT is refused before opening a socket; that transport does
not yet enforce pins.

## Process memory hardening (Linux)

`lib/memory_protection.dart` calls the kernel through FFI:

- `prctl(PR_SET_DUMPABLE, 0)` — prevents same-UID `ptrace`/core inspection
  of the wallet process (subject to kernel policy);
- `setrlimit(RLIMIT_CORE, 0)` — no core files;
- `mlockall(MCL_CURRENT | MCL_FUTURE)` — best effort; may fail under a low
  `RLIMIT_MEMLOCK`, and the app reports failure instead of claiming success.

This is not a secure enclave, not encrypted memory, and does not protect
against a compromised OS or a process running as the same user before the
call. `test/memory_protection_test.dart` reads back the real kernel state.

## Preferences and secrets separation

SharedPreferences (`*Preferences` plugin, plaintext files) may contain ONLY:
`network`, `rpc`, `nodes`, `tokens`, `profiles`, `auto_lock_seconds`,
`tor_enabled`, `tor_host`, `tor_port` — public configuration, no secrets.

Secure storage (`flutter_secure_storage`) contains ONLY:
`device_secret_v2`, `app_lock_pin_hash`, `app_lock_backoff`,
`bscscan_api_key` — all of which "Erase all data" removes.

The live Home history is never written to disk (in-memory only). The receipt
archive (`bnb-wallet-receipts.bin`, `BNBRCPT1`) and the activity log
(`bnb-wallet-log.bin`, `BNBLOG01`) are encrypted at rest with per-file keys
derived from the wallet key plus the device drawer secret; the plain pending-tx
status list holds public data only.

## Vault write path

`AppStorage.writeVaultAtomic`: serialize base64 → write `<file>.tmp`
→ flush → `rename(tmp, file)` (atomic on POSIX; unlink+rename fallback on
platforms refusing replace) → `chmod 600` on Linux/macOS. A crash before
the rename leaves the previous vault byte-identical; after the rename, the
new one.

## Erase all data

1. Overwrite vault + `.tmp` with CSPRNG bytes of equal size (best effort;
   flash wear-leveling prevents guarantees) then unlink both.
2. Delete secure-storage keys. This removes the device factor; it does NOT
   make a retained vault copy undecryptable with the password.
3. Remove every preference key the app owns.
4. Clear in-memory caches and UI state.

Recovery afterward requires the 24-word seed phrase. Nothing in the app
can recover funds without it.

## Honest caveats

- The composition (this repo) has no third-party audit. See THREAT_MODEL.
- Argon2id in a Dart VM is software-level: it provides the standard
  64 MiB/t=3 cost per guess; it is not a memory-hardness innovation.
- CSPRNG is `Random.secure()` (getrandom(2) on Linux/Android).
- On-chain data is public; Tor mode protects the transport path only.

## For Users: Choosing Your Connection Mode

### Quick Decision Guide

| Your Situation | Recommended Mode | Why |
|----------------|------------------|-----|
| **Home, trusted network, no privacy concerns** | Direct | Simplest, lowest latency |
| **Corporate/uni network with proxy** | HTTP/HTTPS Proxy | Required by network policy |
| **Public Wi-Fi, want IP privacy** | Tor | Hides IP from RPC; ISP sees only Tor |
| **Censored country, Tor blocked** | Tor Bridge (obfs4) | Bypasses Tor blocking |
| **Running own VPS/node** | Tor → VPS or SOCKS5 → VPS | VPS sees Tor exit / proxy IP |
| **Maximum privacy, technical user** | Strict Privacy + Tor | All traffic forced, fail-closed |
| **Cold signer (offline device)** | Offline Mode | Zero network access |
| **Watch-only companion** | Direct/Tor/Proxy (no keys) | No signing capability |

## Connection Mode Details

### 1. Direct HTTPS
- **How it works**: App → TLS → RPC endpoint
- **ISP sees**: RPC hostname (SNI), IP, timing, volume
- **RPC sees**: Your real IP, all requests
- **Setup**: Just enter RPC URL (must be HTTPS)
- **Best for**: Trusted home network, local node

### 2. HTTP/HTTPS Proxy (CONNECT)
- **How it works**: App → HTTP CONNECT → Proxy → TLS → RPC
- **ISP sees**: Proxy IP, CONNECT hostname
- **Proxy sees**: Your IP, destination hostname, all traffic (HTTPS proxy: only CONNECT metadata)
- **RPC sees**: Proxy exit IP
- **Setup**: Settings → Network → Proxy → HTTP/HTTPS → host:port (+ auth if needed)
- **Certificate validation**: Always enforced (no bypass)
- **Best for**: Corporate networks, controlled proxy

### 3. SOCKS5 Proxy
- **How it works**: App → SOCKS5 → Proxy → TLS → RPC
- **ISP sees**: Proxy IP
- **Proxy sees**: Your IP, destination hostname (SOCKS5h), all traffic
- **RPC sees**: Proxy exit IP
- **Setup**: Settings → Network → Proxy → SOCKS5 → host:port (+ auth)
- **DNS**: Remote resolution (no local DNS leak)
- **Best for**: General proxy, SSH tunnels (`ssh -D`)

### 4. Tor (System Daemon)
- **Prerequisites**: `sudo apt install tor` (Ubuntu) or Orbot (Android)
- **Default**: SOCKS5 on `127.0.0.1:9050`
- **How it works**: App → Tor SOCKS5 → 3-hop circuit → TLS → RPC
- **ISP sees**: Tor entry guard IP, encrypted Tor traffic
- **Tor entry**: Your IP
- **Tor exit**: RPC destination IP, TLS handshake
- **RPC sees**: Tor exit node IP
- **Setup**: Settings → Network → Tor → Enable (auto-detects 127.0.0.1:9050)
- **Bridges**: Configure in `/etc/tor/torrc` or Orbot; app just uses SOCKS5
- **Fail-closed**: If Tor stops, requests fail — **no direct fallback**

### 5. Tor Bridges
- **obfs4**: `Bridge obfs4 <IP>:<PORT> <FINGERPRINT> cert=<CERT> iat-mode=0`
- **WebTunnel**: `Bridge webtunnel <IP>:<PORT> <FINGERPRINT> url=<URL>`
- **Configure in**: Tor daemon config (`/etc/tor/torrc`) or Orbot
- **App behavior**: Unchanged — still uses local Tor SOCKS5

### 6. Strict Privacy Mode
- **What it does**: Enforces selected route for **ALL** traffic
- **RPC**: Through route
- **Explorer (BscScan)**: Through route
- **Token metadata**: Through route
- **Price APIs**: Through route (if enabled)
- **Update checks**: none exist in this app
- **Fail-closed**: Any route failure = error shown, no fallback
- **Enable**: Settings → Network → Strict Privacy Mode

### 7. Offline Mode
- **What it does**: Blocks all **app-initiated** network calls (RPC, prices,
  explorer history, node probes). It is a runtime gate, not an OS sandbox; for
  a dedicated air-gapped machine, also run the app under `unshare -n` or a
  systemd unit with `PrivateNetwork=yes` (see `docs/COLD_WALLET.md`).
- **DNS**: Not resolved
- **RPC**: Not polled
- **Tor/Proxy**: Not connected
- **Updates**: Not checked
- **Use case**: Cold signer device, air-gapped operation
- **Enable**: Settings → Wallet Mode → Cold (offline signer) — auto-enables

# PRIVACY.md — what this wallet does and does not do with your information

Version 1.0.5 · AGPL-3.0-or-later · Contact: jackh109867@gmail.com

## What we collect: nothing

The wallet has no telemetry, no analytics, no crash reporting, no update
pings, no account, no email. It never calls a server of the developer. The
developer receives nothing, ever. A network capture of a running wallet
shows requests to the RPC nodes and explorer you (or the defaults) selected,
plus optional public price lookups. Price lookups are off by default and are
blocked in cold mode. They send only fixed coin IDs, never an address or
balance.

## What the network layer actually sends

Every HTTP client is constructed in one module (`net/privacy_client.dart`);
`test/data_boundary_test.dart` fails if another construction site appears.
Node proxy passwords, bearer tokens and custom headers are held in the
platform secure store, not in the plain preferences file:

- **No identifying headers.** Requests carry only `content-type:
  application/json` (RPC) or `accept: application/json` (explorer).
  The library default `User-Agent: Dart/x.x (dart:io)` is scrubbed.
- **Tor route (optional, off by default):** with "Route traffic through Tor"
  enabled, the same requests are tunnelled through a local SOCKS5 connector
  (Tor SocksPort, e.g. `127.0.0.1:9050`; Orbot on Android). There is NO
  fallback to a direct connection — if the proxy is down, network calls
  simply fail. Bridges (obfs4/WebTunnel) are configured inside tor/Orbot
  itself; the wallet only needs the local SOCKS port.
- **DNS:** with Tor enabled, hostnames resolve through SOCKS5.
- **Timing:** proxy round trips add latency; the fee engine derives its
  "seconds per block" expectations from realrpc measurements, never from
  hardcoded tables.

## What an RPC node can and cannot learn

CAN see:

- your IP address or Tor exit's IP (when node privacy is on, it sees the
  Tor exit, not you);
- every question you ask it — balance, nonce, gasprice, chain, block,
  fee history, broadcast of signed transactions — and can associate those
  with the addresses involved;
- timing and sequencing of your questions.

CANNOT see:

- your seed words or private keys (nothing leaves the device — signing is
  local; the payload broadcast is opaque);
- what a transaction means to you (mempool observers see data, not context);
- anything above HTTPS payload length/timing when Tor is on.

The wallet narrates all of this in plain words inside Settings → RPC nodes,
shows a **one-time warning per node** before you add one, and offers
**strict mode** (talk ONLY to your chosen node; no fallback doors).

## Where your data lives

- **Vault (encrypted):** `bnb-wallet-vault.bin` — seed/keys sealed with
  XChaCha20-Poly1305 under an Argon2id-derived key (64 MiB, t=3, p=4).
- **Receipt archive (encrypted):** `bnb-wallet-receipts.bin`, key derived
  from wallet secret + a device drawer secret, envelope `BNBRCPT1`, capped
  at 200 entries.
- **Plain preferences:** network choice, chosen RPC, phone book (public
  node addresses + labels), custom token contracts, hidden-token keys, a
  watch-only public address, Lite-mode flag, the pending-tx status list and
  the state discussed above. Nothing secret is in there; the phone book and
  user token links are shareable JSON.
- **API keys** (optional BscScan key): secure on-device storage.
- **Encrypted activity log:** `bnb-wallet-log.bin`, envelope `BNBLOG01`,
  XChaCha20-Poly1305 under a key derived from the wallet key and the device
  drawer secret. Capped at 5 MB / 10 000 entries. It records network, fee,
  transaction and lock events for the in-app Logs screen (Simple and Expert
  views). Signed transactions and secret material are never written to it.
- **Raw RPC panel:** the last 50 request/response pairs are kept in memory
  only for "View raw request", never on disk.
- **Watch-only profile:** its public address is a plain preference; there is
  no key or seed for it on this device.

## Backups

Nothing the wallet stores is uploaded anywhere by it. There is no cloud
backup, no export push, no sync. Exports (node phone book JSON) go to your
clipboard or file only when you trigger them.

## `docs/BACKUP_AND_RECOVERY.md`

# Backup and Recovery

**Scope:** the encrypted local vault, the portable backup, and recovery.
The vault file itself is device-bound; a portable `BNBBKP01` backup depends on
its password only and restores on a new device. The recovery phrase remains the
ultimate backup for HD accounts.

## What is backed up

- Encrypted vault file: `bnb-wallet-vault.bnb` (`BNBVL004` v2).
- Portable backup: `BNBBKP01`, Argon2id + XChaCha20-Poly1305, password only.
  It contains the encrypted account list and restores on a fresh install.
- Encrypted receipt archive and activity log are local; they are not required
  to recover funds.
- The device secret is **not** in the backup. It lives in the platform secure
  store or the Linux owner-only drawer. The portable backup deliberately does
  not need it.

## Canonical recovery procedure

1. Stop the wallet.
2. Keep the original vault file untouched.
3. On a clean installation, choose **Import wallet → recovery phrase**.
4. Enter the 12/24 words in the correct order. Never type them into a website,
   chat, terminal, or support message.
5. Confirm the derived address against an independent record.
6. Send a small test amount before relying on the restored wallet.

Do not restore by copying only the vault file to another machine: the
device-bound wrapper will not open without that machine's device secret. Use
**Export portable backup** instead; it is designed for exactly this case.

## Backup verification

- The portable backup must decrypt with its password on a fresh device and
  re-encrypt under the new device secret.
- A failed export must never replace a known-good backup.
- A failed import must leave the original vault byte-identical; this is covered
  by `test/vault_import_rollback_kdf_test.dart`.
- A wrong password, truncated file, corrupted tag, or modified header must fail
  closed with a generic error.

## Tested

- Vault v2 round-trip, wrong password, wrong device secret, fresh nonce.
- Portable backup round-trip, wrong password, tamper, truncation, and restore
  on a fresh device (`test/portable_backup_test.dart`).
- v1 migration and truncated-header rejection.
- Atomic write, rollback injection, post-commit verification failure.
- Import rollback and concurrent serialization.

## Not tested

- End-to-end UI restore on a clean physical machine (the unit test models a
  fresh device secret, not a full desktop run).
- Disk-full and power-loss recovery on a physical device.
- Backup media failure and long-term paper degradation.

## Recovery limitations

- There is no support recovery, no key escrow, and no password reset.
- Losing both the recovery phrase and the vault password loses the funds.
- A compromised OS can capture the phrase while it is displayed.
- Do not store the phrase in a photo, cloud note, password manager, or chat.

## `docs/COLD_WALLET.md`

# Cold Wallet Mode — operator and developer guide

Status: implemented and self-verified. **Not independently reviewed.** Use on
the current testnet (chain id 97) or with small amounts until an external
review exists. The security assessment is in [`SECURITY_AUDIT.md`](../SECURITY_AUDIT.md).

## What the mode guarantees

- The **cold signer** holds the seed/private key in process memory only while
  unlocked, and has **no network access**: `RpcService` is put offline and
  `connect()` fails closed. It never prepares or broadcasts a transaction.
- The **online companion** holds **no seed and no private key**. It prepares
  an unsigned EIP-1559 request, imports the cold device's signed response,
  independently re-verifies every byte, and only then broadcasts.
- Pairing exports **public addresses only** (plus an optional public xpub).
  No mnemonic, private key, passphrase or vault password crosses the QR/file
  channel.
- A signed response is bound to one request id and one exact set of fields.
  Replay, field substitution, expiry, wrong signer, wrong chain and already
  broadcast bytes are refused.

## The two roles

| Role | Holds | Network | Can sign | Can broadcast |
|---|---|---|---|---|
| Hot (normal) | seed/key while unlocked | yes | yes | yes |
| Cold (offline signer) | seed/key while unlocked | **no** | yes, offline | **no** |
| Online (companion) | public pairing only | yes | **no** | yes, after verification |

Switching modes:

1. Settings → Wallet mode → **Cold (offline signer)**. The wallet disconnects
   and stays offline. If no key is in memory, unlock the vault.
2. On the cold device, export the pairing (QR/file). It contains the first 20
   default BIP-44 addresses and a 4-byte fingerprint.
3. On the online device, switch to **Online (watch-only companion)**. Import
   the pairing and compare the fingerprint on both screens. The first paired
   address becomes the watch-only account.
4. Leaving cold mode locks it. A hot or online session must be explicitly
   unlocked/paired again; keys are not carried across the boundary.

## End-to-end flow

```
online companion                         cold signer (offline)
----------------                         ---------------------
1. build unsigned EIP-1559 request
   (chain, nonce, fees, gas, to,
    value, calldata, asset info)
2. store pending request
3. show QR / file / paste  ───────────▶ 4. import request
                                        5. decode + validate:
                                           version, chain 56/97,
                                           expiry, from is one of
                                           the first 20 addresses,
                                           native/calldata match
                                        6. user reviews recipient,
                                           amount, fee cap, calldata
                                        7. sign with matching
                                           m/44'/60'/0'/0/<index>
                                        8. self-verify the result
                                        9. show signed response
10. import response  ◀──────────────────┘
11. require the exact request still
    pending with identical bytes
12. recompute digest, parse raw tx,
    compare every field, r/s/yParity,
    hash; recover exactly one signer
13. refuse if already broadcast or
    signed after expiry
14. broadcast raw bytes
15. node hash must equal the local
    hash; otherwise report unknown
    outcome and burn the bytes
```

Request lifetime defaults to **30 minutes** and is capped at 24 hours. A
response produced after the request expired (plus 5 minutes of clock skew) is
refused. The online side also refuses a response for a request it no longer
has pending. Keep both devices' clocks reasonably synchronized.

## Protocol envelopes

All three payloads use the same versioned envelope:

```json
{
  "magic": "BNBCOLD",
  "version": 1,
  "kind": "pairing | request | signature",
  "payload": { "...": "..." },
  "checksum": "<sha256 of canonical JSON payload>"
}
```

Rules enforced by [`lib/cold_wallet_protocol.dart`](../lib/cold_wallet_protocol.dart):

- canonical JSON (sorted object keys), SHA-256 checksum;
- exact allow-listed fields; unknown or missing fields are rejected;
- size limits: pairing 8 KiB, request 32 KiB, signature 16 KiB;
- addresses must be valid EIP-55/EIP-20 addresses; duplicates are rejected;
- pairing chain is 56 or 97; request chain is 56 or 97;
- request ids are 8–64 URL-safe characters; expiry must follow creation and
  be at most 24 hours later;
- signed responses carry `requestHash` (the EIP-1559 signing digest) and
  `yParity`; `v` is the full recovery id (0–3), not the legacy 27/28 value;
- native-asset requests carrying calldata are rejected;
- the checksum is an integrity check, **not** an authenticator. Authenticity
  comes from the ECDSA signature over the exact transaction and from the
  paired address fingerprint.

## What is stored where

`ColdWalletService` persists only public data in preferences:

| Key | Content |
|---|---|
| `cold_pairing_v1` | pairing envelope (public addresses, fingerprint) |
| `cold_pending_requests_v1` | unsigned request envelopes, bounded to 20 |
| `cold_signed_responses_v1` | signed response envelopes, bounded to 20 |
| `cold_signed_request_ids_v1` | ids already signed, bounded to 20 |
| `cold_broadcast_hashes_v1` | tx hashes already broadcast, bounded to 20 |

No secrets are written by the cold flow. The vault remains the only place a
seed or private key is persisted, and only in its encrypted envelope.

## Verification before broadcast

The online companion never trusts the cold device's claims. It re-derives:

1. the unsigned payload and `keccak256` digest from the pending request;
2. the parsed raw transaction from the response;
3. every field (chain, nonce, fees, gas limit, recipient, value, calldata,
   access list);
4. `r`, `s`, `yParity`, `v`, and `keccak256(raw)` against the advertised hash;
5. the recovered signer against the paired `from` address.

The independent implementation in
[`verification/verify.cjs`](../verification/verify.cjs) uses **ethers.js
6.17.0** (not web3dart) on a synthetic public test vector. It checks the same
payload/digest/raw bytes/hash/signature/recovered signer and rejects eight
field substitutions. CI runs it on every push.

```sh
cd verification
npm ci
node verify.cjs
```

## Transport channels

- **Display QR** of the envelope text on the sending device.
- **Export to file** (`.json`) through the platform save dialog.
- **Paste** the envelope text or a file path.
- **Camera QR scanning** is not implemented in this Linux build. Use file or
  paste; a phone build would need a camera plugin, which is out of scope here.

QR codes of a full signed transaction can be large. If a QR does not fit,
use the file. The protocol rejects payloads above its size limits rather than
truncating them.

## Failure behavior

| Situation | Behavior |
|---|---|
| Pairing checksum/fingerprint wrong | refuse import; ask for a fresh pairing |
| Request expired | refuse to sign and refuse to verify |
| Request `from` not in first 20 default addresses | refuse to sign |
| Custom derivation path does not match `from` | signer refuses |
| Response bytes differ from pending request | refuse; nothing is broadcast |
| Wrong signer / wrong chain / wrong nonce / substituted field | refuse |
| Replayed request id with different bytes | refuse |
| Already broadcast hash | refuse |
| Node returns a different hash | report unknown outcome; do not resend; bytes burned |
| Cold mode tries to connect | fail closed; no RPC call leaves the device |

## Limits

- Version 1.1.0 enables BSC mainnet (56) and testnet (97); other EVM networks are not yet enabled.
- Only EIP-1559; legacy fee requests are not created for the cold flow.
- Access lists are rejected.
- First 20 default BIP-44 accounts only (`m/44'/60'/0'/0/0..19`). Custom
  derivation paths are not carried in the request.
- No camera QR on Linux.
- No two-physical-device field test has been recorded.
- No third-party audit.

## Network-isolated launcher

Cold mode blocks every app-initiated call at runtime. For a stronger,
OS-enforced boundary, the `.deb` also installs `x-wallet-offline`. It runs the
same binary inside an empty network namespace with only a loopback interface:

```sh
x-wallet-offline
```

It requires `util-linux` and user namespaces. If the namespace cannot be
created, the launcher **fails closed** and tells you to keep the machine
physically offline; it never falls back to a networked run.

For a dedicated cold machine, the stronger procedure is:

1. Use a machine that has no Wi-Fi/Bluetooth hardware enabled and no network
   cable; disable the interfaces in the firmware/OS as well.
2. Boot a clean, fully updated OS from removable media if possible.
3. Run `x-wallet-offline` (or `unshare -n -- x-wallet`) and verify that the
   only interface in the namespace is `lo`.
4. Move signing requests and responses only by USB or by displaying/copying
   the payload, and verify the payload hash on the cold screen before signing.
5. Never connect the cold machine to a network, even briefly, for updates.

## What each area proves

### Cold transaction codec

`test/cold_tx_codec_test.dart` pins the exact EIP-1559 payload and digest for
a known public vector, and rejects non-canonical RLP, wrong field lengths and
invalid signature scalars.

`verification/verify.cjs` is the independent oracle. It imports only
ethers.js, parses the raw signed transaction emitted by the Dart codec,
recomputes the payload/digest, checks `r`/`s`/`yParity` and the transaction
hash, recovers the signer, and repeats the digest/recovery check after
changing each of eight signed fields (recipient, value, chain, nonce, gas,
fees and calldata). It does not use web3dart or the Dart codec.

### Cold protocol and service

`test/cold_wallet_protocol_test.dart` covers envelope integrity, expiry,
unknown/missing fields, duplicate addresses, native/calldata mismatch,
checksum tampering and `v`/`yParity` disagreement.

`test/cold_wallet_service_test.dart` covers persistence, bounded storage,
single-use request ids, offline signing, replay with different bytes, a
foreign signer, response verification against a changed request, a response
for a non-pending request, future timestamps, strict broadcast, a mismatched
node hash (bytes burned), and a tampered response that must never reach the
node (the fake RPC records zero broadcasts).

### TLS pinning

`test/tls_pinning_test.dart` generates an ephemeral CA and server certificate
with OpenSSL, verifies that Dart and OpenSSL compute the same SPKI SHA-256
pin, and proves:

- a correct pin succeeds only after standard TLS validation;
- a wrong pin fails even though the chain is trusted;
- a correct pin cannot bypass hostname validation;
- a correct pin cannot bypass CA validation;
- an empty pin list fails closed;
- pinned HTTP CONNECT is refused before any socket is opened.

### Memory hardening

`test/memory_protection_test.dart` reads the actual kernel state of the test
process: `PR_GET_DUMPABLE` is 0 and the core-file soft limit is 0. It does not
prove that every page is locked; `mlockall` is best-effort and may fail under
a low `RLIMIT_MEMLOCK`.

### Widget and dialog tests

`test/widget_test.dart` boots the app with mock preferences and no network.
`test/privacy_dialogs_test.dart` opens the proxy/Tor dialogs and checks the
options and URL parsing. `AppStorage.init()` deliberately skips the OS keyring
under `FLUTTER_TEST`; without that, the test runner's fake-async zone can wait
forever on an unserviced platform channel.

## What is not tested

- **No third-party audit.** The tests are written by the same project that
  wrote the code.
- **No real-chain broadcast.** The broadcast gate is tested with a fake RPC.
  `anvil` is not installed, so no local EVM accepted or rejected a signed
  transaction in this run.
- **No two-device cold transfer.** File/paste/QR display paths are exercised
  in code/tests, not by carrying a file between two physical machines.
- **No camera QR scanning on Linux.**
- **No APK/deb build in this run.** The release keystore is intentionally not
  in the repository; `scripts/build-apk.sh` requires an external keystore.
- **No Windows/macOS run.** The memory-hardening test is Linux-only.
- **No hardware wallet.**

## Interpreting failures

- `TimeoutException ... Test timed out` in a KDF test usually means the
  machine is too slow or another derivation is running. Re-run the KDF phase
  alone with `--concurrency=1`; do not lower the Argon2id parameters to make a
  test pass.
- `Bad state: Cannot close sink while adding stream` from the Flutter test
  runner means the runner was killed mid-test (often by a timeout), not that
  an assertion failed. Read the earlier output for the real cause.
- Any failure in `verification/verify.cjs` means the signed bytes, digest,
  fields or recovered signer drifted. Do not "fix" the fixture without an
  independent reason; investigate the codec first.
